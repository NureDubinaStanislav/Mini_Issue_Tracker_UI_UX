# Mini Issue Tracker — UX Architecture / Screen Map

**Документ:** `02_Screen_Map_v0.3.2.md`  
**Версія:** 0.3.2 — погодження доступності Create Issue у порожньому списку (D-10)  
**Дата:** 14.10.2026  
**Статус:** документальна перевірка пройдена; для фінального людського погодження (Контроль B)  
**Основа:** `01_Input_Pack_v0.1.md` та Decision Log D-01–D-10 зі статусом `APPROVED`.

> **Статус достовірності.** Цей документ описує UX-архітектурну пропозицію для Release MVP. Він не є підтвердженням погодження кожним учасником команди або викладачем. Ураховано лише рішення Decision Log зі статусом `APPROVED`; інші питання залишаються unresolved. D-09 усуває невизначеність щодо Create/Cancel у M-01, а D-10 підтверджує доступність Create Issue в S-02-C Empty.

## 1. Принципи та межі Release MVP

1. **Release Scope:** US-01–US-08 за §8 Input Pack. Candidate MVP і Release MVP — послідовні етапи визначення обсягу; Q-01 не трактовано як блокувальну суперечність. US-09 `Attach files` — `Deferred`; SR-10 і SR-11 — `Future`, тому вони не з’являються в екранах, переходах або демонстраційних сценаріях.
2. **Погоджені поверхні:** S-01 Authentication boundary; S-02 Issues List зі станами S-02-A All, S-02-B Important і S-02-C Empty; M-01 Create modal; S-03 Issue Details. Assignment, Priority, Status і Comments — пов’язані контролі/секції на S-03, а не самостійні сторінки.
3. **Одна User Story не дорівнює одному screen.** Пов’язані дані, поля й дії для assignee, priority, status і comments розміщуються в Issue Details з рольовими та статусними компонентними станами.
4. **Role gating (D-05):** недоступні рольові дії видимі, але `disabled`. Пояснення міститься в службовій annotation REF-01 / Review Notes, а не у вигаданому tooltip або додатковій продуктовій сторінці.
5. **Apply (D-06):** для assignee, priority і status користувач обирає значення й натискає відповідний `Apply`. Після успішної зміни він залишається на S-03; оновлюється стан даних.
6. **Back (D-07):** вихід із S-03 повертає до попереднього стану S-02 — All або Important.
7. **Create navigation (D-09):** після успішного створення M-01 закривається й відкривається S-03 для щойно створеної issue. `Cancel` закриває M-01 без створення issue та повертає до попередньої вкладки списку All або Important.
8. **Create Issue в Empty (D-10):** кнопка присутня в спільній шапці S-02 для All, Important і S-02-C Empty; вона видима й активна для обох автентифікованих ролей за відсутності рядків. Нову окрему кнопку в empty area не додавати.
9. **Прототип демонстраційний (D-08):** використовуються фіктивні навчальні дані й наперед підготовлені результати. Це не доводить наявність реальної автентифікації, backend, БД чи persistence.

### Позначення

- **Screen/page** — окрема продуктова сторінка.
- **Screen state** — стан тієї самої сторінки, а не нова сторінка.
- **Modal/overlay** — модальне вікно поверх поточного screen.
- **Component state** — стан конкретного контролу/секції на screen або в modal.
- **Service/Review annotation** — службова примітка поза продуктовим UI; не додає продуктової поведінки.
- **Approved** — рішення позначене `APPROVED` у Decision Log. Це не означає, що весь цей документ затверджений.

Cancel можна показати як дію в F-05 із прототипним з’єднанням назад до попереднього list state; успішний Create веде до S-03 у F-07.

| F-03 | S-02-B Important із даними | Перевірка High/Critical, включно з Resolved, та виключення Closed |

Компонентні варіанти `CS-ASSIGNEE-NONE`, `CS-PRIORITY-NOTSET` і проміжні стани селекторів можна показати в межах відповідних frames як component variants/interactive states. Вони не потребують окремих основних frames. Якщо кожен проміжний вибір буде зафіксовано статично, frames може стати більше, але кількість продуктових сторінок від цього не змінюється.

## 3. Специфікація surface/state

Для кожного запису нижче наведено: **Screen/State ID | Name | Purpose | Actors | Entry | Visible data | Inputs | Actions | Role/state conditions | Errors/empty states | Exit | Source/D-ID**.

### 3.1. S-01 — Authentication boundary

- **Screen/State ID:** `S-01`
- **Name:** Authentication boundary — `Authentication entry — mechanism TBD`
- **Purpose:** Позначити межу автентифікації та те, що функції MVP доступні лише автентифікованим членам команди. Це placeholder, а не дизайн входу.
- **Actors:** Неавтентифікований відвідувач на межі; далі — автентифікований Team Member або Team Lead.
- **Entry:** Зовнішній вхід до застосунку / початок демонстраційного маршруту до автентифікованої частини.
- **Visible data:** Лише підпис `Authentication entry — mechanism TBD` і службова примітка, що механізм не визначений. Не показувати email/password, SSO або відновлення доступу.
- **Inputs:** Немає продуктових полів вводу.
- **Actions:** Немає функціональної login-дії в макеті. Перехід до S-02 можливий лише як позначена межа після факту автентифікації, не як змодельований спосіб входу.
- **Role/state conditions:** До автентифікації основні функції недоступні. Спосіб автентифікації не визначено.
- **Errors/empty states:** Login errors не моделюються, оскільки login UI не погоджено.
- **Exit:** Після автентифікації — S-02; механізм переходу поза межами цього UX-макета.
- **Source/D-ID:** BR-01, NFR-02, R-01; D-02 (`APPROVED`).

### 3.2. S-02-A — Issues List / All

- **Screen/State ID:** `S-02-A`
- **Name:** Issues List — All
- **Purpose:** Перегляд усіх зареєстрованих issues та відкриття обраної issue у S-03.
- **Actors:** Автентифіковані Team Member і Team Lead.
- **Entry:** Після автентифікації; після вибору вкладки All; або повернення з S-03, якщо попереднім станом списку був All; також після Cancel із M-01, якщо modal було відкрито з All.
- **Visible data:** Для кожної issue щонайменше ID, Title, Status, Priority, Assignee (коли призначений). Вкладки All / Important. `Not Set` для priority не означає Low. Сортування не припускається.
- **Inputs:** Вкладка All/Important; вибір рядка/issue; `Create Issue`.
- **Actions:** Перемкнути вкладку; відкрити S-03; відкрити M-01.
- **Role/state conditions:** Лише автентифіковані члени команди. Обидві ролі можуть переглядати список і створювати issue.
- **Errors/empty states:** Якщо в поточному scope немає записів, відображається S-02-C. Точний текст empty-state не визначено.
- **Exit:** S-02-B через вкладку Important; M-01 через Create Issue; S-03 через issue; залишається в S-02-A після Cancel з M-01.
- **Source/D-ID:** US-01, US-02, US-08, AC-02.1–AC-02.3; D-01, D-02, D-03, D-08, D-09 (`APPROVED`).

### 3.3. S-02-B — Issues List / Important

- **Screen/State ID:** `S-02-B`
- **Name:** Issues List — Important
- **Purpose:** Швидкий перегляд важливих issues за погодженим критерієм priority/status.
- **Actors:** Автентифіковані Team Member і Team Lead.
- **Entry:** Вибір вкладки Important на S-02; повернення з S-03, якщо попереднім станом списку був Important; також після Cancel із M-01, якщо modal було відкрито з Important.
- **Visible data:** Issues із priority `High` або `Critical`, якщо status **не** `Closed`. `Open`, `In Progress` і `Resolved` можуть бути показані. `Low`, `Normal`, `Not Set` і будь-який `Closed` не показуються.
- **Inputs:** Вкладка All/Important; клік по issue; `Create Issue`.
- **Actions:** Перейти до All; відкрити S-03; відкрити M-01.
- **Role/state conditions:** Та сама рольова доступність, що й у S-02-A. Фільтрація визначається правилами, а не додатковими користувацькими фільтрами.
- **Errors/empty states:** Якщо жодна issue не відповідає критеріям, використовується S-02-C із вкладкою Important як активним контекстом. Не показувати `Closed` у цьому списку.
- **Exit:** S-02-A через вкладку All; S-03 через issue; M-01 через Create Issue; залишається в S-02-B після Cancel з M-01.
- **Source/D-ID:** US-08, BR-09, BR-09.1, AC-08.1–AC-08.4; D-01, D-07, D-08, D-09 (`APPROVED`).

### 3.4. S-02-C — Empty list state

- **Screen/State ID:** `S-02-C`
- **Name:** Issues List — Empty
- **Purpose:** Показати порожній результат списку без створення окремої сторінки.
- **Actors:** Автентифіковані Team Member і Team Lead.
- **Entry:** Завантаження S-02-A, коли issues немає; або S-02-B, коли немає жодної issue з priority High/Critical і status не Closed.
- **Visible data:** Структура S-02, активна вкладка (All або Important) та факт відсутності записів. Точний empty-state copy не визначено.
- **Inputs:** Перемикання All/Important; `Create Issue` завжди доступна в спільній шапці S-02 за D-10, навіть якщо рядків немає.
- **Actions:** Перейти на іншу вкладку; натиснути Create Issue і відкрити M-01 без додаткового empty-state CTA.
- **Role/state conditions:** Стан визначається даними поточного scope, а не роллю. Empty All означає відсутність зареєстрованих issues; Empty Important може виникнути, коли issues є, але жодна не проходить критерій Important. Create Issue активна для обох автентифікованих ролей незалежно від результату списку (D-10).
- **Errors/empty states:** Сам цей стан є empty state. Текст на кшталт `No issues yet` не вважається затвердженим копірайтом.
- **Exit:** M-01 через Create Issue; після Cancel повертається до того самого попереднього list state; після успішного Create відкривається S-03 нової issue за D-09; зміна вкладки веде до S-02-A або S-02-B залежно від результату.
- **Source/D-ID:** AC-02.5; US-01, US-08, AC-08.1–AC-08.4; D-01, D-08, D-09, D-10 (`APPROVED`). Точний текст Empty — unresolved.

### 3.5. M-01 — Create Issue modal

- **Screen/State ID:** `M-01`
- **Name:** Create Issue modal
- **Purpose:** Створення issue з обов’язковими Title і Description у modal поверх поточного стану S-02.
- **Actors:** Автентифіковані Team Member і Team Lead.
- **Entry:** Клік `Create Issue` на S-02-A, S-02-B або S-02-C. Modal запам’ятовує попередній list state для Cancel.
- **Visible data:** Поля Title і Description; дії `Create` і `Cancel`. Нова issue починається без assignee і з priority Not Set. Не показувати assignee-пікер або встановлення priority у формі створення.
- **Inputs:** Title (обов’язковий); Description (обов’язковий).
- **Actions:** `Create` за валідних обов’язкових полів; `Cancel` закриває modal без створення issue й повертає до попередньої вкладки списку.
- **Role/state conditions:** Будь-який автентифікований член команди може створити issue. Cancel доступний обом ролям і не створює запис.
- **Errors/empty states:** Для порожнього Title показується `Title is required`. Порожній Description блокує створення, але точний текст і механізм помилки не визначені.
- **Exit:** Невалідна форма → M-01-V; успішне створення → modal закривається й відкривається S-03 нової issue; Cancel → попередній list state S-02-A, S-02-B або S-02-C. Успішний Create і Cancel визначені D-09.
- **Source/D-ID:** US-01, AC-01.1–AC-01.5; BR-02–BR-04; D-01, D-03, D-04, D-08, D-09 (`APPROVED`).

### 3.6. M-01-V — Create validation error

- **Screen/State ID:** `M-01-V`
- **Name:** Create Issue — validation error
- **Purpose:** Показати, що невалідна форма не створює issue та залишається відкритою для виправлення.
- **Actors:** Поточний автентифікований користувач.
- **Entry:** Користувач натискає Create з порожнім Title та/або Description.
- **Visible data:** M-01 із полями; для порожнього Title — `Title is required`. Якщо порожні обидва поля, Description також має бути позначено як невалідний, але точний текст не підставляється без рішення.
- **Inputs:** Title і Description для виправлення.
- **Actions:** Повторна спроба Create після виправлення; Cancel повертає до попереднього list state без створення.
- **Role/state conditions:** Однаково для Team Member і Team Lead.
- **Errors/empty states:** Точний текст для Title відомий. Для Description, whitespace, довжин і форматування правила не визначені.
- **Exit:** Валідна форма → успішний submit і S-03 нової issue; Cancel → попередній list state; повторний невалідний submit → цей самий state.
- **Source/D-ID:** AC-01.1–AC-01.3, BDD-сценарій з `Title is required`; D-08, D-09 (`APPROVED`); деталі валідації залишаються unresolved.

### 3.7. S-03 — Issue Details (базовий стан нової issue)

- **Screen/State ID:** `S-03`
- **Name:** Issue Details
- **Purpose:** Єдине місце перегляду issue та пов’язаних контролів призначення, priority, status і Comments.
- **Actors:** Автентифіковані Team Member і Team Lead; право на окремі дії залежить від ролі та assignee.
- **Entry:** Вибір issue зі S-02; після успішного Create — безпосередньо з M-01 за D-09.
- **Visible data:** ID, Title, Description, Status, Priority, Assignee (якщо є), Author, Created at; коментарі з текстом, автором і датою/часом. Для новоствореної issue: Status `Open`, Priority `Not Set`, Assignee відсутній.
- **Inputs:** Comment text. Для Team Lead — вибір assignee та priority. Для поточного assignee — вибір дозволеного status transition. Title/Description не редагуються через відсутність відповідної User Story.
- **Actions:** Apply біля assignee, priority і status; submit comment; Back до попереднього стану S-02. Після Create modal закрито, нова issue відкрита в S-03.
- **Role/state conditions:** Team Lead може призначити одного виконавця, якщо assignee ще немає, або замінити поточного assignee іншим членом команди; очищення assignee не передбачено. Team Lead також може встановити/змінити priority. Лише поточний assignee змінює status за дозволеними переходами. Якщо assignee відсутній — status change недоступний для всіх. Comments доступні обом основним ролям.
- **Errors/empty states:** Priority `Not Set` і відсутній assignee — валідні дані, не помилки. Невдале збереження comment показує CS-COMMENT-ERROR. Недозволені рольові дії видимі/disabled. Точні тексти більшості помилок не визначені.
- **Exit:** Back → попередній list state за D-07. Успішні Apply для assignee/priority/status залишають користувача на S-03. Comment success/error також залишається в S-03. Після успішного Create S-03 є безпосередньою ціллю навігації за D-09.
- **Source/D-ID:** US-02–US-07, AC-02.4, AC-05.1–AC-05.3, AC-06.1–AC-06.5; BR-03–BR-08.1; D-03–D-09 (`APPROVED`).

### 3.8. S-03-ST-OPEN — Issue Details / Open, actor є assignee

- **Name:** Issue Details — Open (assignee context)

- **Inputs:** Status selector із дозволеним target `In Progress`; Apply.

- **Role/state conditions:** Роль Team Lead сама по собі не дає права змінювати status, якщо він не assignee.

### 3.9. S-03-ST-INPROGRESS — Issue Details / In Progress

- **Role/state conditions:** Status змінює лише поточний assignee; іншим користувачам control visible/disabled.
- **Errors/empty states:** Не дозволяти In Progress → Closed напряму.

### 3.10. S-03-ST-RESOLVED — Issue Details / Resolved

- **Screen/State ID:** `S-03-ST-RESOLVED`
- **Name:** Issue Details — Resolved
- **Purpose:** Розрізнити Resolved і Closed та показати можливість повернення issue в роботу.
- **Actors:** Поточний assignee.
- **Entry:** Apply `Resolved` зі S-03-ST-INPROGRESS або відкриття Resolved issue.
- **Visible data:** Усі поля S-03; status Resolved. Якщо priority High/Critical, issue досі відповідає умові Important, доки не Closed.
- **Inputs:** Status selector із двома дозволеними target: `In Progress` і `Closed`; Apply.
- **Actions:** Apply `In Progress` для повернення в роботу; або Apply `Closed`; коментарі; Back.
- **Role/state conditions:** Status змінює лише поточний assignee.
- **Errors/empty states:** Будь-який target поза In Progress і Closed заборонений і не має пропонуватися.
- **Exit:** Apply `In Progress` → S-03-ST-INPROGRESS; Apply `Closed` → S-03-ST-CLOSED; Back → попередній list state.
- **Source/D-ID:** BR-08.1, BR-09.1, AC-07.3–AC-07.5, AC-08.1–AC-08.4; D-05, D-06, D-07 (`APPROVED`).

### 3.11. S-03-ST-CLOSED — Issue Details / Closed

- **Purpose:** Показати фінальний дозволений status і наслідок для Important list.

- **Visible data:** Усі поля S-03; status Closed.
- **Inputs:** Comment text; для status немає дозволеного наступного target.
- **Actions:** Перегляд деталей, коментарі за загальними правилами, Back.
- **Role/state conditions:** Closed не має вихідного status transition у BR-08.1; status control неактивний/без доступних targets.
- **Errors/empty states:** Не пропонувати переходів зі Closed. Після повернення до Important issue не відображається.
- **Exit:** Back → збережений попередній S-02 state; якщо це Important, закрита issue відсутня в результаті.

### 3.12. S-03-R-DISABLED — Role-restricted controls

- **Errors/empty states:** Не симулювати повідомлення після кліку по disabled control — дія не запускається. Пояснення — у REF-01 / Review Notes.

## 6. Текстові user flows

### UF-01. Створення та перегляд issue

1. Автентифікований Team Member або Team Lead починає з `S-02-A All` (або може почати з `S-02-B Important`).
2. Натискає `Create Issue` → `T-01` → `M-01`. Поточна вкладка запам’ятовується.
3. Вводить Title і Description.
4. Якщо Title порожній: `M-01 → T-02 → M-01-V`; issue не створюється, показано `Title is required`. Після виправлення користувач може повторити Create.
5. Якщо поля валідні: `M-01 → T-03 → S-03`. Modal закривається, відкривається саме нова issue зі `Status = Open`, `Priority = Not Set`, без assignee; присутні ID, author і created-at.
6. Успішне створення не повертає користувача спочатку до списку: destination — S-03 за D-09. З S-03 Back повертає до збереженого list state за D-07.

### UF-02. Cancel створення без створення issue

1. Користувач відкриває M-01 з `S-02-A`, `S-02-B` або `S-02-C` через `T-01`.
2. Натискає `Cancel` у M-01 або M-01-V.
3. Виконується `T-04`: modal закривається, issue не створюється, користувач повертається до попереднього list state — All, Important або відповідного Empty context.
4. Не відкривається S-03, оскільки нової issue немає.

### UF-03. Призначення або перепризначення assignee користувачем Team Lead

1. Team Lead відкриває issue зі списку: `S-02-A → T-07 → S-03` або `S-02-B → T-07 → S-03`.
2. Якщо assignee не заданий, компонент перебуває в `CS-ASSIGNEE-NONE`. Team Lead обирає одного члена команди й натискає Apply — це первинне призначення.
3. Якщо assignee вже заданий, Team Lead може обрати іншого члена команди й натиснути Apply — нове значення замінює поточного assignee. Очищення assignee не передбачено.
4. В обох випадках `T-08` оновлює assignee, а користувач залишається на S-03.
5. Team Member не має доступу до зміни assignee: control visible/disabled, і недозволена дія не змінює дані (`N-01`).

### UF-04. Установлення priority користувачем Team Lead

1. Team Lead відкриває `S-03`; нова issue може показувати `CS-PRIORITY-NOTSET`.
2. Обирає одне значення `Low / Normal / High / Critical` і натискає Apply.
3. `T-09` оновлює Priority на S-03; окрема priority-сторінка не відкривається.
4. Team Member бачить control, але він disabled (`N-01`). `Not Set` не означає `Low`; reset до Not Set немає.

### UF-05. Дозволений перехід Open → In Progress

1. У підготовленому actor context поточний користувач є assignee issue зі статусом Open: `S-03-ST-OPEN`.
2. Обирає `In Progress` і натискає Apply.
3. `T-10` приводить до `S-03-ST-INPROGRESS`; той самий S-03 залишається відкритим.
4. Resolved/Closed напряму з Open не пропонуються (`N-03`).

### UF-06. Дозволений перехід In Progress → Resolved

1. Поточний assignee перебуває на `S-03-ST-INPROGRESS`.
2. Обирає `Resolved` і натискає Apply.
3. `T-11` приводить до `S-03-ST-RESOLVED`. Наступні дозволені target-и — лише In Progress або Closed.
4. Прямий In Progress → Closed не пропонується (`N-04`).

### UF-07. Повернення Resolved у роботу

1. Поточний assignee на `S-03-ST-RESOLVED` обирає `In Progress` і натискає Apply.
2. `T-12` повертає issue до `S-03-ST-INPROGRESS`, не змінюючи сам screen.
3. Якщо actor не є assignee, status control visible/disabled і переходу не відбувається (`N-02`).

### UF-08. Закриття issue зі статусу Resolved

1. Поточний assignee на `S-03-ST-RESOLVED` обирає `Closed` і натискає Apply.
2. `T-13` приводить до `S-03-ST-CLOSED`.
3. Back до `S-02-B Important` зберігає вкладку, але закрита issue не відображається.
4. Closed → In Progress не передбачений (`N-05`).

### UF-09. Успішне додавання comment

1. Користувач відкриває S-03 і вводить непорожній comment.
2. У prepared success-сценарії submit активує `T-14`.
3. `CS-COMMENT-SUCCESS` показує comment із текстом, author і датою/часом; користувач залишається на S-03.
4. Точний формат часу й поведінка поля після submit unresolved.

### UF-10. Помилка збереження comment

1. Користувач відкриває S-03, вводить непорожній comment і submit-ить його.
2. У prepared failure-сценарії виконується `T-15`.
3. `CS-COMMENT-ERROR` показує помилку; новий comment не з’являється у списку.
4. Точний текст помилки та збереження введеного тексту в полі не задаються цим планом.

### UF-11. Перегляд Important

1. На `S-02-A All` користувач обирає Important → `T-05`.
2. У `S-02-B` видно лише priority High/Critical зі status, відмінним від Closed. Resolved з High/Critical залишається в списку.
3. Low, Normal, Not Set і Closed виключені. Це вкладка, а не окрема сторінка чи набір ручних фільтрів.
4. Відкриття рядка приводить до S-03 через `T-07`; Back через `T-17` повертає в Important (або Empty, якщо результатів немає).

### UF-12. Заборонена дія для неуповноваженого користувача

1. Team Member, який не є Team Lead і не є assignee, відкриває issue → `S-03-R-DISABLED`.
2. Assignee, priority і status controls visible/disabled згідно з D-05; коментарі доступні за загальними правилами.
3. Заборонена дія не породжує переходу й не змінює дані (`N-01`, `N-02`). Для пояснення використовують `REF-01`, не tooltip і не нову сторінку.

### UF-13. Порожній список

1. Після входу користувач потрапляє до `S-02-A`; якщо в prepared dataset немає issues, список показує `S-02-C` через `T-18`.
2. Порожня вкладка Important також використовує `S-02-C`, але active tab лишається Important.
3. Create Issue обов’язково видима та активна в спільній шапці навіть у S-02-C за D-10. Клік веде через `T-01` до M-01; Cancel повертає до попереднього Empty/list context через `T-04`; успішний Create веде прямо до S-03 через `T-03`.
4. Точний empty-state copy unresolved.

### UF-14. Повернення до попереднього list state

1. Користувач відкриває issue з All: `S-02-A → T-07 → S-03`. Back через `T-16` повертає до S-02-A (або S-02-C, якщо список порожній).
2. Користувач відкриває issue з Important: `S-02-B → T-07 → S-03`. Back через `T-17` повертає до S-02-B (або S-02-C).
3. Не скидати вкладку до All за замовчуванням. Якщо issue стала Closed, вкладка Important зберігається, але закрита issue не показується.

## 7. Три приклади того, чого НЕ додавати

1. **Attachment upload / список файлів / preview / download.** US-09 позначена Deferred у Release Scope; не включати навіть як декоративну секцію в Issue Details.
2. **AI-категоризація або AI-рекомендація priority.** SR-10 і SR-11 належать до Future, не до Release MVP.
3. **Окремі сторінки Assignment, Priority, Status або Comments.** Це пов’язані контролі/секції на S-03; самостійні сторінки не входять до погодженого варіанта.

## 11. Source/D-ID index

- **US-01 / AC-01.1–AC-01.5:** створення issue, поля, статус Open, ID/author/created-at, початковий Not Set; D-09 визначає destination після Create і Cancel.
- **US-02 / AC-02.1–AC-02.5:** список, мінімальні поля, відкриття деталей, empty state.
- **US-03:** один assignee, призначення Team Lead-only; перепризначення для навчального UX-макета — D-04.
- **US-04 / AC-04.1–AC-04.2:** priority та права Team Lead.
- **US-05 / AC-05.1–AC-05.3:** відображення status у list/details.
- **US-06 / AC-06.1–AC-06.5:** comment, author/time, empty rejection і save error.
- **US-07 / AC-07.1–AC-07.5; BR-08.1:** status transition rules та права assignee.
- **US-08 / AC-08.1–AC-08.4; BR-09 / BR-09.1:** Important = High/Critical і status не Closed; Resolved може входити.
- **D-01:** desktop grayscale low-fi; одна Issues List з All/Important; Create Issue через modal.
- **D-02:** S-01 — тільки Authentication boundary placeholder; не вигадувати login mechanism.
- **D-03:** Not Set окремо від Low; allowed priority values; без reset.
- **D-04:** нова issue без assignee; Team Lead може призначити одного виконавця або перепризначити на іншого члена команди; без clear assignee.
- **D-05:** недоступні дії visible/disabled; пояснення в REF-01.
- **D-06:** Apply для assignee/priority/status; після успіху залишатися на S-03.
- **D-07:** Back із S-03 зберігає попередній list state All/Important.
- **D-08:** fake навчальні дані та наперед підготовлені прототипні результати; без реального backend/persistence.
- **D-09:** після успішного Create modal закривається й відкривається S-03 нової issue; Cancel закриває modal без створення issue й повертає до попередньої вкладки All/Important.
- **D-10:** Create Issue завжди доступна у спільній шапці S-02, у тому числі за S-02-C Empty; DEF-G4-01 закрито.

**Перед наступним етапом:** D-09 визначає Create/Cancel, D-10 уточнює Create Issue в Empty. DEF-G4-01 усунено; інші відкриті питання залишаються без змін.
